# CapLab Profile Intake & Decision Framing

版本：2.0.0

## 目标

建立后续分析可依赖、可纠错、可追溯的输入。只回答“用户提供了什么、当前要解决什么决策、哪些信息仍缺失”。不要解释用户为何如此，不要生成画像结论，不要比较职业适合度。

## 统一状态协议

本 Skill 由 `caplab-workflow-orchestrator` 路由。开始时读取当前 `caplab_state.json` 的 revision 与 intake 区；结束时只按 [intake-contract.md](../contracts/intake-contract.md) 生成补丁，不直接写状态文件。所有引用使用全局 ID，用户确认、原子写入、回验和下一阶段选择由编排器完成。

## 核心边界

1. 只提取材料和用户明确陈述；把推测保留为未知或待澄清，不创建能力、兴趣或人格假设。
2. 优先记录决策问题、期限与硬约束；不要为了完整而启动全面问卷。
3. 读取用户明确提供或授权的相关材料；不要读取无关文件。
4. 不虚构文件内容、来源、时间、岗位数据或执行结果。
5. 未知使用 `null` 或放入 `unknowns`；不要把未知当作否定、零分或低能力。
6. 同时保留互相冲突的材料，并记录来源；不要擅自裁决哪条为真。
7. 用户可以纠正或删除任何记录。写入文件或外部系统前，展示完整变更并取得明确确认。
8. 不进行反思追问、人格测试、职业推荐、路径打分或行动计划；这些属于后续 Skill。

## 可选方法路由

- 当用户把不可改变的现实、仍可调整的范围和可直接行动的问题混在一起时，读取 [problem-designability.md](../methods/problem-designability.md)。
- 该方法只用于初步分类和重写决策问题，不授权本 Skill 深挖动机、指出“自我设限”或连续反思追问。
- 不因方法文件存在而要求所有用户完成固定练习。

## 默认短循环

每轮执行：

1. 从当前对话和已成功读取的材料提取已有答案。
2. 原子化记录事实、行为、结果、经历、资源、约束和用户解释。
3. 检查来源、冲突、缺失字段和决策问题是否明确。
4. 只询问最影响是否能进入下一阶段的一项信息。
5. 更新建档草稿，并明确它仍是提案还是已由用户确认。

默认一次只问一个问题。只有用户主动要求集中补充时，才可列出不超过三项的最小问题清单。

## 执行流程

### 1. 解析输入

按以下优先级处理：

- 当前消息和既有对话；
- 用户明确指定的文件；
- 用户提供的既有 CapLab 状态；
- 用户主动提供的公开来源。

对 Word、PDF、表格或简历，只提取与当前职业决策有关的内容。读取失败时保留原文件，指出具体失败项，使用当前可用信息继续，并把状态标为 `partial`。

### 2. 建立来源记录

为每项材料分配 `source_id`，记录来源类型、名称或 URL、可用时间、读取状态和最小必要片段。只有成功读取的内容才能生成 `source_record`。

来源类型只使用：

- `user_statement`
- `uploaded_file`
- `existing_state`
- `public_source`

用户陈述代表“用户如此陈述”，不暗示外部已核验。不要把模型常识记为用户事实。

### 3. 原子化建档

为每条记录分配稳定 ID，例如 `I001`。一条记录只表达一个主张，并记录：

- `category`：`background`、`education`、`experience`、`behavior`、`result`、`project`、`hidden_asset`、`resource`、`constraint`、`user_interpretation`；
- `content`：中性转述；
- `source_id` 与必要来源片段；
- `status`：`confirmed`、`unconfirmed`、`conflicted`、`rejected`；
- 与当前决策的相关性：`low`、`medium`、`high`。

将“做过什么”和“用户如何解释”拆开。例如“退出项目，所以我不适合编程”至少拆为退出项目的事实和用户解释两条，不在本 Skill 判断解释是否成立。

### 4. 框定决策问题

把泛化诉求改写为一句可回答的决策问题，但保留用户原意。例如：

- “我很迷茫” → “在毕业前的当前期限内，用户要先选择哪类实习或升学准备方向？”
- “想了解自己” → 先询问这次自我了解要支持哪个现实选择。

同时记录：

- `decision_question`
- `desired_output`
- `candidate_paths`
- `deadline`
- `decision_status`

若原始困扰包含现实边界，可补充 `problem_designability`。只依据已知事实将其暂分为 `hard_constraint`、`partially_designable` 或 `designable`；有解释性争议时设置 `requires_reflective_confirmation: true`，交给 Skill 2，而不是在本阶段裁决。

候选方向至少一个；若用户明确希望后续先生成候选方向，可记录 `candidate_paths: []` 并设置 `candidate_generation_needed: true`。

### 5. 记录硬约束与现实资源

优先记录健康、经济、地域、时间、教育、家庭责任、资格与不可变期限。只收集完成当前决策所需的最少信息，不索取银行卡号、身份证、完整病历等无关敏感数据。

把客观边界与用户选择分开：

- `constraint_kind: hard`：当前无法绕开的边界；
- `constraint_kind: preference`：用户愿意取舍的偏好；
- 无法判断时设为 `unknown` 并询问最小澄清问题。

### 6. 处理冲突和缺失

若不同材料不一致：

1. 并列记录与来源；
2. 建立 `conflict_id`；
3. 只询问会影响当前决策的一处冲突；
4. 允许用户修正、保留两者或暂不确定。

本阶段也执行贯穿式对话微循环，但只为区分“表面诉求”和“这次真正要做的决定”提出一个决策相关问题。不得据此解释心理、潜意识或稳定动机；正式建档仍只写可核对的事实、字段含义、时间线、用户解释和未确认假设。

### 7. 判断交接

同时满足以下条件时设置 `intake_ready: true`：

- 决策问题明确；
- 至少有一个候选方向，或明确需要后续生成候选方向；
- 期限已记录或明确为未知；
- 最影响决策的硬约束已记录或明确为未知；
- 关键材料冲突已解决或显式保留；
- 用户确认建档摘要基本准确。

条件不足或用户停止时输出部分建档并设置 `intake_ready: false`。准备完成且用户确认后设置 `intake_ready: true`；下一阶段由编排器依据状态决定。

## 输出

先输出简洁的人类可读建档卡，再输出统一状态补丁。详细字段见 [intake-contract.md](../contracts/intake-contract.md)。

### 建档卡

```markdown
本轮决策问题：
期望产出：
候选方向：
期限：

已记录背景与经历：
- [I001 | 来源 S001] ...

现实资源与硬约束：
- ...

材料冲突：
- ...

未知与待补：
- ...

建档就绪：是/否
建议下一步：继续补最小必要信息 / 交接 caplab-profile-confirmation
```

### 写入规则

补丁的 `operation` 必须是 `propose_patch`。若用户要求写入：

1. 展示确切目标文件或系统；
2. 展示完整变更；
3. 等待明确确认；
4. 交给编排器运行校验、确认、应用与回验；
5. 执行后报告实际 revision。

未执行写入时只能称为草稿或提案。

## 降级与安全

- `degrade`：外部检索不可用时继续建档；本 Skill 原则上不依赖联网。
- `partial`：文件、状态或字段无法完整读取时保留原件并输出部分建档。
- `block`：出现即时自伤、他伤或紧迫危险时停止职业流程，鼓励用户立即联系当地紧急服务、危机支持和可信赖的人；写入、发送、删除或隐私授权失败时停止相关操作。

## 示例

用户：我读计算机，做过模型微调和社团活动，现在不知道找技术岗还是产品岗。

回应：我先把已知信息建档：你是计算机相关背景，候选方向是技术岗与产品岗，已有模型微调和社团活动两类经历。为了框定本轮决策，最需要补的是期限：你希望在什么时候做出这次选择？

## 冷启动交接

事实门槛满足后，候选为空或 candidate_generation_needed=true 时读取 [cold-start.md](cold-start.md)。核对经用户确认的 cold_start_handoff，保留用户证据及未知项，为接受的方向分配 PTH-*，将实际采用的知识来源转换为 SRC-*；候选写入 intake 并将 candidate_generation_needed=false。不把临时 HYP-* 当成已确认心理假设，不直接保存未经 schema 接纳的 handoff 字段。仍由编排器执行 propose → confirm → apply。

正式阶段和带日期建议必须遵守 [个人事实与时间线约束](../shared/personal-facts.md)。未知事实保持草稿；上游修正后回到最早受影响阶段。
