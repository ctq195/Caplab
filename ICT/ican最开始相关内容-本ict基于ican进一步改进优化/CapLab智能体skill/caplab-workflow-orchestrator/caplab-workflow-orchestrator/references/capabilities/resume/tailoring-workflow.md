# 岗位定制工作流

## 一、岗位要求拆解

将 JD 拆成下列字段，不把推断写成招聘方明示：

| 字段 | 含义 |
|---|---|
| requirement | 职责、必备条件或加分项原意 |
| level | must / preferred / inferred |
| evidence_needed | 能支持该要求的经历、产物或结果 |
| keywords | 候选关键词与同义表达 |
| source | JD 原文位置、用户提供文本或网页来源 |

同一个关键词出现多次不等于重要性必然更高。先看职责和必备条件，再看出现频次。

## 二、证据矩阵

每项要求只允许以下状态：

- `direct`：简历或用户材料已经直接支持；
- `supportable`：用户可能拥有相关证据，但必须追问或确认后才能写入；
- `transferable`：存在相邻能力，可诚实表述为迁移能力；
- `gap`：没有证据，保留为真实缺口；
- `not_relevant`：无需放入本版简历。

为每条拟改写保存 `source_evidence`。无法指出来源时，不把它作为事实写进最终简历。

## 三、内容决策

按以下顺序筛选，后面的因素不能抵消前面的事实缺口：

1. 对 JD 必备职责和条件的覆盖；
2. 证据是否已确认、是否能指出来源；
3. 技术是否处于任务关键路径，而非只在技能表出现；
4. 是否说明个人行动、决策、约束和可核验结果；
5. 奖项或成果认可度、时效性；
6. 每行能传达的有效岗位信息。

内容超量时依次删除重复技能、弱相关课程、无成果且低相关的经历、同类经历中的弱项。不得先靠缩小字体解决内容选择问题。允许：

- 调整经历和要点顺序；
- 使用 JD 中与真实经历一致的标准称谓；
- 把冗长叙述改为“行动—方法—结果—范围”；
- 删除与目标岗位低相关且占版面的内容；
- 将同一真实经历针对不同岗位选择不同侧面。
- 将未选内容留在主版本，并在 `selection_log` 记录保留、隐藏或删除的理由。

禁止：

- 复制 JD 句子并冒充经历；
- 为满足关键词新增未使用过的工具或技术；
- 把团队成果全部归为个人成果；
- 把课程练习包装成生产项目，把计划包装成已完成结果。

## 四、评审方式

在最终版前给出简短变更表：原文、建议文本、理由、证据来源、确认状态。用户已经明确要求直接制作时，可以先生成新版本，但不得覆盖主简历；所有不确定事实仍留在“待确认”，不能进入事实正文。

信息不足时只追问会改变岗位匹配、量化结果、个人贡献或时间线的高价值问题，每轮最多 3 个。已知信息足够形成诚实版本时不要为了填满字段而持续追问。

经历条目优先包含动作、技术/方法、对象/任务和结果；其中任一部分缺失时允许保留真实的较短表达。不得把团队结果全部归给个人，也不得把定性结果伪装成精确数字。

最终按 [scoring-rubric.md](scoring-rubric.md) 进行启发式评分。总分不能掩盖具体证据缺口或事实硬门槛。
