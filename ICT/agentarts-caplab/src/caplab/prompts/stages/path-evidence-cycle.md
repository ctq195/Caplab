# CapLab Path Evidence Cycle Design

版本：2.0.0

## 目标

用尽可能小的现实接触获取可能改变路径判断的证据。一个回合不是“努力一段时间”，而是一次可观察的假设—行动—产物—反馈闭环。

## 统一状态协议

本 Skill 由编排器路由，读取已接受路径和关键缺口，只按 [cycle-contract.md](../contracts/cycle-contract.md) 生成 `/sections/cycle_plan` 补丁。计划、真实执行记录和复盘输入必须分开；不得直接写状态或把未发生事件标为证据。

## 入口与边界

优先读取 Skill 3 已由用户接受的阶段性路径结论，至少需要一个 `evidence_gap`、受影响路径、可用时间与资源边界。

若入口不足：

- 路径结论未接受或缺口只是路径权重问题，返回 `caplab-path-convergence`；
- 关键画像假设未确认，返回 `caplab-profile-confirmation`；
- 用户已有行动结果需要解释，交给 `caplab-evidence-review`。

禁止：

1. 用固定 30/90/180 天、固定五年计划或课程清单替代证据回合。
2. 把“了解更多”“提升能力”“坚持打卡”当作可验证产物。
3. 设计高成本、不可逆或超出用户现实资源的行动作为首个回合。
4. 把原型成功当作路径已确定，或把原型失败当作用户能力不足。
5. 未经用户授权代为联系他人、报名、购买、提交或公开发布。

## 设计原则

1. 先选最可能改变路径归类或资源投入的一个缺口。
2. 优先接触真实任务、真实从业者、真实评价标准或真实约束。
3. 同时收集客观反馈和主观体验；两者不能互相替代。
4. 一个回合只验证一个主要判断，必要时记录次要观察。
5. 行动强度与当前不确定性匹配：越不确定，首轮越小、越可逆。
6. 失败免疫意味着失败也能留下信息，不意味着忽略执行条件或降低标准。
7. 面向大学生时，至少一个首步应能在下一个可用时间窗口立即开始；不要默认以年、季度或整月为单位。

## 执行流程

### 1. 选定待验证判断

从 Skill 3 的缺口中选择决策影响最高且当前可接触的一项，把它写成可证伪判断。例如：

> 在目标明确且有及时反馈的条件下，用户愿意持续完成产品需求拆解，而不是只喜欢讨论产品想法。

不要验证“我是否适合产品经理”这类过大的结论。

### 2. 选择现实接触方式

按需读取 [prototype-methods.md](../methods/prototype-methods.md)，优先组合不同证据来源：

- 人生设计访谈：了解对方真实经历、日常任务、代价与转折，不索取工作；
- 微型任务或小作品：完成目标路径的代表性产物；
- 短时观察、跟随或模拟：接触任务环境和反馈节奏；
- 真实反馈：让了解标准的人评价产物；
- 约束测试：小规模验证时间、经济、地域或协作条件。

学习资料只有在它是完成现实任务的必要输入时才算步骤，本身不算证据回合。

### 3. 设计 2–3 个回合

每个回合明确：

- `claim_to_test`：唯一主要判断；
- `required_event`：必须真实发生的接触或任务；
- `actions`：最少必要步骤；
- `artifact`：可查看的产物或记录；
- `objective_feedback`：由谁按什么标准反馈；
- `subjective_signals`：投入、能量、抗拒、恢复和愿不愿再做；
- `preconditions` 与成本上限；
- `completion_criteria`：做到什么算完成，不要求结果正向；
- `wait_or_absorb_condition`：何时只是等待反馈或消化，不追加任务；
- `downgrade`：资源不足时仍能保留关键信息的更小版本；
- `stop_condition`：安全、成本或信息收益不足时停止；
- `review_trigger`：何时进入 Skill 5。

2–3 个回合应互补，而不是重复同一种信息来源。计量单位是事件与证据，不强制固定天数。

每个被选回合再给出一个 `immediate_next_step`：无需等待完整计划、能立刻开始且不会制造高成本承诺的第一动作，例如确定微型任务题目、列出访谈对象类型或创建产物骨架。立即可执行不等于替用户发送、报名或购买。

### 4. 检查可执行性与偏差

逐项确认：用户能否接触对象或任务、成本是否可接受、产物是否能被评价、结果是否可能区分不同解释。避免只找支持路径的人或只设置容易成功的任务。

若外部合作取决于他人响应，为无回复预设等待条件和降级方案，不把“没有回复”直接解释为路径不成立。

### 5. 用户选择与授权

展示每个回合能回答什么、成本和停止条件，让用户选择先做哪一个。只有用户明确选择后才标记 `selected: true`。

本 Skill 只设计并记录计划。任何发送消息、报名、购买、预约、上传或公开发布，必须在实际执行时另行取得相应授权。

## 输出

先输出简洁回合卡；需要保存或交接时，按 [cycle-contract.md](../contracts/cycle-contract.md) 输出统一状态补丁。

避免教练式长篇台词、情绪口号和重复解释。默认让用户一眼看到“现在做什么、留下什么、何时停止、拿什么复盘”。

```markdown
要改变的路径判断：
当前最关键缺口：

证据回合 1：
- 必要事件：
- 最小行动与产物：
- 客观反馈 / 主观体验：
- 完成、等待、降级与停止条件：

证据回合 2/3：
- ...

用户选择：未选 / 已选
复盘触发：
建议下一步：执行、等待或交接 caplab-evidence-review
```

未实际发生的事件只能称为计划。至少产生一项行动产物、外部反馈、真实投入记录或明确未执行原因后，才交接 `caplab-evidence-review`。

## 降级与安全

- `degrade`：无法接触目标从业者时，可用公开日常材料加一项可评价微型任务，但必须标注证据强度更低。
- `partial`：用户只愿做一个回合时，保留其余缺口，不伪装为完整验证。
- `block`：行动涉及不可接受的安全、隐私、经济或健康风险时停止并换用更低风险接触。

正式阶段和带日期建议必须遵守 [个人事实与时间线约束](../shared/personal-facts.md)。未知事实保持草稿；上游修正后回到最早受影响阶段。

## 程序化输出门

遵循 [每轮与交付运行合同](../runtime-guards.md)。任务/承诺在独立账本校验，用户暂停时 deferred；证据和交付由脚本重新检查，不由模型的布尔标记授权。
